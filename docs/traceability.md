# Requirements traceability matrix

V-model trace from each approved requirement in `docs/prd/lifescape-place-discovery.md` down to its
architecture and design, its code, and the tests that verify it. `tests/test_traceability.py`
fails when a requirement is missing, its quoted text no longer matches the PRD, or any reference
does not resolve to a real file and symbol. Update this table in the same change as any
requirement, design, code, or test change (PRD section 11).

```text
requirements (PRD) ─▶ architecture/design (ADR, docs) ─▶ code ─▶ unit/integration tests
        ▲                                                              │
        └───────── system and acceptance tests (browser journeys) ◀────┘
```

## Field notes

- FR18 (BUI-2149): each `discover_towns` match and each `profile.exemplars` entry returns
  `latitude` and `longitude` from the packaged catalog, or `null` when the catalog has none, so
  Claude can draw a map in chat. The FR18 row traces the tests that prove both fields.
- FR16 (BUI-2199): the read-only hosted landing page (`src/lifescape/templates/landing.html`) has
  one static "Use it in Claude" section after the hero, with no inputs and no new routes. It links
  the desktop extension and skill from the README's "Install in Claude Desktop" steps and lists
  three example asks. `tests/test_landing_claude_section.py` checks the heading, the asks, and that
  every link matches the README.
- FR17 surface, hosted (BUI-2207): the hosted MCP server's OAuth (`src/lifescape/oauth.py::allowed_redirect`)
  also accepts ChatGPT's redirects, `https://chatgpt.com/connector_platform_oauth_redirect` and
  `https://chatgpt.com/connector/oauth/{callback_id}`, and still refuses every other non-Claude,
  non-loopback redirect. The metadata already listed S256, `/register` and auth method `none`, and
  tokens were already bound to the server's resource. `tests/test_oauth_chatgpt.py` proves all three
  (REQ-CHATGPT-1..3).
- Hosted store, per user (BUI-2211): `research_packets` and `run_report_indexes` have an `owner`
  column holding the signed-in user's token `sub` (`''` for no user). `src/lifescape/store_db.py::DatabaseStore`
  reads and writes only the caller's rows, so another user's packet or run ID reads as not found.
  A run ID hashes the run's inputs, so run indexes are keyed by (owner, run ID); packet IDs are
  random, and a save never replaces a packet another user owns. `src/lifescape/mcp_server.py::create_server`
  takes the user from the access token and refuses a hosted token with no subject. A database
  made before the column existed migrates once, in one transaction, and its rows go to
  `OWNER_GITHUB_LOGIN`; with rows and no owner set, the store refuses instead of guessing. Rows
  saved later with no user stay the no-user's rows. The stdio server has no user and is unchanged.
  `tests/test_store_per_user.py` proves it (REQ-USER-1..3).
- Hosted store, delete my data (BUI-2213): `src/lifescape/store_db.py::DatabaseStore.delete_user_data`
  deletes every `research_packets` and `run_report_indexes` row the user owns, in one
  transaction, and counts them; other users' rows stay. `src/lifescape/mcp_server.py::create_server`
  adds the `delete_my_data` tool only on the database store (the local files are the user's own);
  it takes the user from the access token, refuses a token with no subject, needs `confirm` true,
  and returns the user and both counts. The privacy page (`src/lifescape/templates/privacy.html`)
  says that with signup open any GitHub account can sign in, that each user's records are stored
  under their GitHub login and only they can read them, and that `delete_my_data` removes them.
  The landing page's "Use it in Claude" section and the README give
  `https://lifescape.buildproven.ai/api/mcp` as the claude.ai connector and keep the desktop
